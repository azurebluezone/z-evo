# S1 — লক স্ক্রিন: লগইন ছাড়া খোলা যায়, GET দিয়ে চালু হয়

## এখন কী হচ্ছে (আগে)

```php
// routes/web.php:929  — গ্রুপে 'auth' মিডলওয়্যার নেই
Route::get('locked', [DashboardController::class, 'locked'])->name('locked');
```

```php
// DashboardController::locked() — আগে
public function locked(){
    // only if user is logged in
     Session::put('locked', true);
     return view('backEnd.auth.locked');
    return redirect()->route('login');   // return-এর পরে: কখনোই চলে না
}
```

```php
// DashboardController:24 — কর্তৃপক্ষের ইচ্ছা ছিল, কিন্তু লাইনটা মন্তব্য করা
// $this->middleware('auth')->except(['locked','unlocked']);
```

## কেন সমস্যা

১. **`auth` মিডলওয়্যার নেই।** রুটটি `['customer','ipcheck','check_refer']` গ্রুপে ছিল — তাই
   লগইন না করেই `/admin/locked` খুলত। লক স্ক্রিন ভিউতে পৌঁছানো যেত যে কেউ।

২. **GET।** `LockAccount` মিডলওয়্যার প্রতিটি অ্যাডমিন রিকোয়েস্টে
   `Session::get('locked') === true` দেখে এখানে রিডাইরেক্ট করে। লক সেট করা একটি
   *state change* — HTTP-তে এর জন্য POST ও CSRF টোকেন লাগে। GET হওয়ায় যে কোনো লিংক,
   ব্রাউজারের prefetch, বা ইমেইলের `<img src="/admin/locked">` — কোনো কিছুতেই ব্যবহারকারীর
   সম্মতি লাগে না। লগইন করা একজন অ্যাডমিনকে ইমেইলে একটি লিংক পাঠালেই তার সেশন লক হয়ে যায়।

৩. **`return` এর পরে dead code** — লেখা ছিল "only if user is logged in", কিন্তু `Auth::check()`
   কখনো ছিল না; নিচের `redirect()` কখনোই চলত না।

## সমাধান

- দুটি রুটই অথেন্টিকেটেড অ্যাডমিন গ্রুপে নেওয়া হয়েছে।
- `lock` মিডলওয়্যার থেকে বাদ দেওয়া (`->withoutMiddleware`), নইলে লক স্ক্রিন নিজেই নিজেকে
  রিডাইরেক্ট করে infinite loop হতো।
- লক করা এখন **POST** (`/admin/locked`), আর ছাড়া **POST** (`/admin/unlocked`, পাসওয়ার্ডসহ) —
  দুটোই CSRF সুরক্ষিত।
- কন্ট্রোলারের ভেতরে `Auth::check()` বাড়ানো হয়েছে — মিডলওয়্যার বদলালেও গার্ড থাকে।
- dead code সরানো হয়েছে।
- navbar ও master-এর দুইটি "Lock Screen" লিংক POST ফর্মে বদলানো হয়েছে।

**প্রমাণ:** `tools/admin_state_changing_gets.php` আর লক স্ক্রিনের নতুন রুট তালিকা;
ব্রাউজারে POST ছাড়া `/admin/locked` এখন 405, লগইন ছাড়া POST এখন 302।

# S2 — GET রুটে সাতটি স্টেট পরিবর্তন

## এখন কী হচ্ছে (আগে)

`tools/admin_state_changing_gets.py` প্রতিটি অ্যাডমিন GET রুটের কন্ট্রোলার মেথডের
শরীর পড়ে খুঁজে বের করে কোনগুলো আসলেই ডেটাবেসে লেখে:

| রুট | মেথড | GET-এ যা ঘটে |
|---|---|---|
| `admin/order-bulk-destroy` | `OrderController@bulk_destroy` | **অর্ডার + এর OrderDetails + Shipping + Payment মুছে ফেলে** |
| `admin/order-status` | `OrderController@order_status` | স্ট্যাটাস বদলায়, "on-the-way" হলে স্টক কমায় |
| `admin/order-assign` | `OrderController@order_assign` | অর্ডারে ইউজার অ্যাসাইন করে |
| `admin/products/update-status` | `ProductController@update_status` | বাল্ক প্রোডাক্ট স্ট্যাটাস |
| `admin/products/update-feature` | `ProductController@update_feature` | বাল্ক ফিচার প্রোডাক্ট |
| `admin/products/update-deals` | `ProductController@update_deals` | বাল্ক হট ডিলস |
| `admin/bulk-courier/{slug}` | `OrderController@bulk_courier` | কুরিয়ার পাঠানোর পরে `$order->save()` |

## কেন সমস্যা

`admin/order-bulk-destroy?order_ids[]=5` — এই একটা URL ইমেইলে বা চ্যাটে পাঠালেই অর্ডার ও
এর সব সংশ্লিষ্ট রেকর্ড মুছে যায়। কোনো নিশ্চিতকরণ নেই, কোনো CSRF টোকেন নেই, কোনো audit
নেই। ব্রাউজারের prefetch বা কোনো লিংক প্রিভিউ এটা চালু করতে পারে। বাকিগুলোও একই
শ্রেণির — শুধু ধ্বংস না, ব্যবসায়িক তথ্য বদলে যায়।

## সমাধান

- সাতটি রুটই **POST**-এ সরানো হয়েছে। POST-এ CSRF টোকেন বাধ্যতামূল, তাই বাইরের কেউ ট্রিগার
  করতে পারে না।
- যে AJAX/ফর্মগুলো এগুলোকে কল করত, সেগুলো পদ্ধতি ও টোকেনসহ আপডেট করা হয়েছে।
- `bulk_destroy`-এ এখন নিশ্চিতকরণ: SweetAlert2 ইতিমধ্যে ছিল, এখন এই পথেও সেটি বসানো হয়েছে।
- `admin_state_changing_gets.py` এখন **শূন্য** রিপোর্ট করে — এটাই রিগ্রেশন গার্ড।

**প্রমাণ:** `python3 tools/admin_state_changing_gets.py` → "none found"।

# K1 — অর্ডার পাইপলাইনে Kanban নেই

## এখন কী হচ্ছে

- `public/admin/assets/vendor/libs/jkanban/jkanban.js` **আছে**, `hammer.js` (jkanban-এর
  নির্ভরতা) **আছে** — কিন্তু পুরো অ্যাডমিনে `jkanban` শব্দের **০টি** রেফারেন্স।
- অর্ডার একটি টেবিল হিসেবে আছে, স্ট্যাটাস বদলাতে প্রতি অর্ডারে মডাল খুলতে হয়।
- `order_statuses` টেবিলে ৬টি স্ট্যাটাস: Pending, Unpaid, On The Way, On Hold,
  Completed, Cancelled।
- স্ট্যাটাস বদলের লজিক (`order_status()`) আগে থেকেই ছিল, এবং "On The Way"-তে গেলে
  স্টক কমানোর কাজও করে — এটা ব্যবহার করেই বোর্ড বানানো হয়েছে, যেন দুই জায়গায়
  স্টকের হিসাব আলাদা না হয়।

## কেন সমস্যা

প্রতিটি অর্ডারের স্ট্যাটাস বদলাতে ৪-৫ ক্লিক, আর ৫০-৫০০ অর্ডার থাকলে পুরো তালিকার
চিত্র মিলিয়ে নেওয়া অসম্ভব। ফলে "কোন অর্ডার কোন অবস্থায় আছে" — এই একটি প্রশ্নের
উত্তর স্ক্রিনে নেই।

## সমাধান

- নতুন পেজ `/admin/order/board` — প্রতিটি স্ট্যাটাস একটি কলাম, অর্ডার একটি কার্ড।
- কার্ডে: অর্ডার নম্বর, কাস্টমারের নাম, মোট টাকা, আইটেম সংখ্যা, তারিখ।
- jkanban + hammer.js দিয়ে ড্র্যাগ-অ্যান্ড-ড্রপ; ছেড়ে দেওয়ার সময় নতুন স্ট্যাটাসে
  সেভ হয়।
- সেভ হলে পুরো স্টক-হিসাব লজিকটাই চলে (On The Way ⇒ স্টক কমবে), কারণ বোর্ডের নতুন
  endpoint কন্ট্রোলারের একই মেথডকে কল করে।
- ব্যর্থ হলে কার্ড জায়গায় ফিরে আসে এবং SweetAlert2 ভুলটা দেখায় — টেনাফলি হলো
  "কার্ড অদৃশ্য হয়ে গেছে কিন্তু ডেটাবেসে পরিবর্তন হয়নি"।

# P1 — প্রোডাক্ট গ্রিডে দাম/স্টক ইনলাইন বদলানো যায় না

## এখন কী হচ্ছে

- গ্রিডে দাম ও স্টক দুটোই **পঠ্য মাত্র** (`৳{{$value->new_price}}`, ব্যাজ)।
- দাম/স্টক বদলানোর আলাদা পেজ আছে (`products.price_edit`) — কিন্তু সেটি **সব** সক্রিয়
  প্রোডাক্ট একসাথে টেবিলে ঢোকে, কোনো পেজিং নেই, আর সেভ করতে সেই পুরো ফর্মই
  পোস্ট হয়।
- গ্রিডে `stock` সর্ট করা যায় (`$sortable[5] = 'stock'`), তাই কম-স্টকের পণ্য খুঁজে
  বের করা যায় — কিন্তু ঠিক সেখান থেকেই স্টক ঠিক করা যায় না।

## কেন সমস্যা

স্টক কমে গেলে ব্যবস্থাপককে আলাদা পেজে গিয়ে, সব পণ্যের ফর্ম স্ক্রল করে নিজেরটা খুঁজে
বদলাতে হয়। ২০০ পণ্যের ফর্ম একবারে পোস্ট হয়। এটাই সবচেয়ে বেশি ঘন হওয়া কাজ।

## সমাধান

- গ্রিডের দাম ও স্টক ঘরে সরাসরি ইনপুট — click-to-edit।
- একটি নতুন POST endpoint একটি প্রোডাক্টের `new_price` ও `stock` বদলায়, পুরো
  ফর্ম নয়।
- যাচাই: দাম ঋণাত্মক বা স্টক ঋণাত্মক হতে পারে না; সংখ্যা না হলে 422।
- বদলানোর পর সেই সারির HTML সার্ভারে আবার তৈরি হয়, তাই গ্রিডে যা দেখাচ্ছে আর ডেটাবেসে
  যা আছে — মিলে যায় (গ্রিড সবসময় সার্ভার থেকে আসে, ব্রাউজারে ক্যাশ নেই)।

# F1 — অর্ডার ফর্ম: `bs-stepper` ফাইল আছে, ব্যবহার নেই

## এখন কী হচ্ছে

- `public/admin/assets/vendor/libs/bs-stepper/bs-stepper.css` ও `.js` **আছে**,

  ধাপ আলাদা করা যায়: **পণ্য**, **ক্রেতার তথ্য**, **ডিসকাউন্ট ও হিসাব**।

## কেন সমস্যা

পণ্য বাছাই করার কাজ শুরু করলে ক্রেতার ঠিকানা লেখার জন্য পুরো পাতা নামতে হয়, আবার
উপরে ফিরে এসে পণ্য যোগ করতে হয়। ফর্মটা যত বড়, তত বেশি ভুল হয়।

## সমাধান

- পুরো ফর্মকে BS Stepper-এর ধাপে ভাগ করা হয়েছে: ১) পণ্য ২) ক্রেতার তথ্য
  ৩) ডিসকাউন্ট ও হিসাব।
- **ফর্মের কোনো ফিল্ড, নাম, ভ্যালিউ বা সাবমিট লজিক বদলায়নি** — শুধু উপরের উপস্থাপনা।
  এটাই যাচাইযোগ্য অংশ: সাবমিটের পর যে ডেটা যায়, আগের মতোই যায় (কোড
  `tools/verify_order_form_fields.php`)।
