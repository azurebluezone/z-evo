## Step 1 — Coupon: stop the client from choosing the discount (P1)

**Evidence (measured):** `POST /apply-coupon` with `subtotal: 999999` returned
`{"amount": 99999.9}` for a 10%-off coupon; with the honest cart value it returned
`100`. Root cause `app/Http/Controllers/Frontend/CouponController.php:17` (reads
`$request->input('subtotal')`) feeding `:56`.

**Do:** compute the subtotal server-side from `Cart::instance('shopping')` and
drop the field from the cart JS.

**Close when:** the inflated-subtotal probe returns the discount for the real
cart only; cart page still applies/removes without console errors.

## Step 2 — Coupon: record and count redemptions (P1)

**Evidence:** `grep -rn used_count app resources/views` has no writer outside
`Admin\CouponController` (which forces `0` on create), so `usage_limit` is
decorative; `orders` has `discount` but no `coupon_id` / `coupon_code`
(`describe orders`).

**Do:** add nullable `coupon_id`/`coupon_code` to `orders`; write them plus
`used_count + 1` inside the existing order transaction.

**Close when:** an order row shows its code and `coupons.used_count` moves 0→1;
`usage_limit: 1` refuses the second apply.

## Step 3 — Coupon: re-validate at placement, clamp the amount (P1)

**Evidence:** `CustomerController.php:355` consumes `Session::get('discount')`
verbatim; `:395` computes `amount = subtotal + shipping - discount` with no clamp,
so a discount captured before a cart change can drive the total to zero or below.

**Do:** reload the coupon by session id, re-run `running()` +
`isUsageAvailable()` + `calculateDiscount($realSubtotal)`; on failure drop the
discount and tell the user; clamp `amount` at 0.

**Close when:** deactivating a coupon between apply and checkout yields
`discount = 0`; a shrinking cart cannot produce a negative amount.
